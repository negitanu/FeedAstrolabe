## Context
設定の深いアンカーリンクを多用し、SNS画面にOpenRouter、運用画面に通知・バックアップなど異なる目的を混在させていた。前回のテストは到達性のみで、画面の意味・作業の連続性を保証していなかった。
## Goals / Non-Goals
Goals: 1ページ1目的、設定名と画面名の一致、3クリック以内、初回の完了可能性、保存後の連続性。
Non-Goals: 秘密鍵をUIに露出すること、データ構造の変更、外部承認の省略。
## Decisions
- 独立した /settings/<section> と /settings/<kind>/<id> を用意し、専用シェルで見出し・パンくず・設定ナビ・次の操作を表示する。
- フォームはpartialsに抽出して単一の定義を使う。機能画面には設定フォームを残さず、明示的な設定リンクを置く。
- /sources/new/<kind> にRSS・SNS・固定ページ・Mastodon登録を分離する。空状態のライブラリと作業ハブに最初の一歩を示す。
- 保存は既存POST処理を維持し、固定した内部URLに戻す。OpenRouterの検証エラーは入力を保持した専用画面で表示する。
- 個別設定は索引から直接開く。登録済み情報源では1件の設定だけを表示する。
- URL・h1・設定ナビ・POST後の行き先をテスト契約にする。空DBからの登録/編集/利用をブラウザーで実行する。
## Risks / Trade-offs
- 既存ブックマーク → section付き旧URLは新画面へ誘導する。アンカーのみの古い設定URLは索引に残した対応リンクで案内。
- 抽出したフォームの欠落 → POSTフィールド・CSRF・既存回帰テストを確認。
- 未設定の外部サービス → 状態と必要な設定場所を明示し、意図せず実行しない。
