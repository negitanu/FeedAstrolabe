## Context
空の Git リポジトリから、個人向け RSS リーダーの第一段階を構築する。macOS でローカル起動し、第二段階でコンテナ化する。

## Goals / Non-Goals
**Goals:** フィード管理、定期収集、検索、閲覧状態を持つ日本語 UI と永続化。
**Non-Goals:** 第一段階では外部公開、複数ユーザー、SNS、ブラウザー観測を実装しない。

## Decisions
- Flask のサーバー描画と SQLite を採用。SPA と PostgreSQL も検討したが、個人利用では単一の Python 環境と DB ファイルで運用できる構成を優先する。
- feeds と articles を分離し、(feed_id, guid) を一意にする。再取得時は記事内容を更新し、既読・スターは保持する。GUID がなければリンク、さらにタイトルと本文の SHA-256 を使う。
- 更新ワーカーを Web と別プロセスにする。SQLite の短いトランザクション、WAL、更新全体のファイルロックで並行実行を調整する。最小更新間隔は 60 秒、既定 900 秒。手動更新も同じロックを使う。
- HTTP は 80/443 の public IP に限定し、DNS 解決結果を検査して同じ IP に接続する。TLS のホスト名検証を保持し、リダイレクトごとに再検査する。最大 5 回、取得 10 秒、本文 5 MiB、ネットワーク処理 30 秒の上限（OS の DNS 解決時間を除く）。ETag/Last-Modified を保存して 304 を処理する。
- 全変更操作は POST とセッション CSRF トークンで保護。記事 HTML は bleach で許可要素に限定し、外部画像、スクリプト、埋め込みを表示しない。URL は HTTP(S) のみ。CSP を設定する。
- ローカル専用として 127.0.0.1 に bind する。認証は第二段階の Cloudflare Access と併せて設計する。

## Risks / Trade-offs
- 同期の手動取得は複数の遅いフィードで時間がかかる → 一件あたり時間制限、ワーカーを常用し、処理中はロック取得失敗を明示。
- SQLite は大量の記事や複数ユーザーには不向き → 第一段階を個人向けとし、ページ送りと索引を入れる。
- フィード配信側のエラー → 最終成功時刻とエラーを分けて記録し、既存記事を保持する。
- 現段階にログインはない → localhost 限定の起動手順とし、外部公開は第二段階の受入条件を満たしてから行う。

## Migration Plan
新規 DB を起動時に作成し user_version=1 を記録。以後は明示的な DB マイグレーションを追加する。データと秘密鍵は instance/ に置き Git 対象外とする。ロールバックは Web/worker を停止し DB バックアップとコードを復元する。
